# AGENTS.md

Fluent C# API that **generates Inno Setup (`.iss`) scripts**. The deliverable is a single NuGet package
(`InnoSetup.ScriptBuilder`); there is no app, server, or DB — everything is fluent builders plus reflection-based text output.

The library currently tracks **Inno Setup 6.3.0**; the migration to **7.1.1** is planned and tracked task-by-task in
`TASKS.md` (one commit per section of that file).

## Layout

- `src/InnoSetup.ScriptBuilder` — the package (`netstandard2.0`). `Builder/` is the public API (one builder per ISS section + `Abstractions/` interfaces), `Model/` holds per-section data classes, `Constants/` mirrors ISS enums/strings, `Utils/` has the entrypoints (`BuilderUtils`, `ValueExtensions`).
- `tests/BuilderTests` — xunit + FluentAssertions (`net10.0`). `TestBuilder.cs` is the single fixture that fills every section; most test classes just assert against its output.
- `examples/Examples/` — console project (`net10.0`) that references the library and mirrors the snippets in `README.md`. `README.md` is packed into the NuGet package (`PackageReadmeFile`), so README edits ship to consumers.
- `examples/DemoApp/` (WPF, `net10.0-windows`, `win-x64`, self-contained single file) is the *payload* installed by the demo setup, not a consumer of the library. It sets `EnableWindowsTargeting=true`, which is why it *compiles* on Linux, but it cannot be published/run here.
- `build/Build.cs`, `build/Build.Demo.cs` — **Fallout** (`Isotopes`) build orchestration, project `build/_build.csproj`. `build.sh` / `build.ps1` / `build.cmd` are thin wrappers around it. The tool is a local tool pinned in `.config/dotnet-tools.json` (`fallout.globaltool`).
- `graphify-out/` — local knowledge-graph index, gitignored; ignore it unless asked about the codebase graph.

## Commands (Linux/macOS)

```bash
# build library + tests
dotnet build tests/BuilderTests/BuilderTests.csproj

# run tests
dotnet test tests/BuilderTests/BuilderTests.csproj

# single test class
dotnet test tests/BuilderTests/BuilderTests.csproj --filter FullyQualifiedName~FilesTests

# whole solution — works on Linux: all four buildable projects compile (DemoApp too, see below)
dotnet build InnoSetup.ScriptBuilder.slnx

# verify the package (README + version)
dotnet pack src/InnoSetup.ScriptBuilder/InnoSetup.ScriptBuilder.csproj -o /tmp/out
```

The Fallout build (`bash build.sh`, or `dotnet tool restore && dotnet fallout <Target>`) is **Windows-only** for real work: the default target `BuildSetup` publishes `DemoApp`, renders `setup.iss`, and then runs Inno Setup `ISCC.exe` from the `Tools.InnoSetup` package. `Test` and `Pack` are the only targets that make sense locally.

## Environment traps (verified, will bite you)

- The root `.editorconfig` is the single IDE-agnostic formatting source (`end_of_line = lf`, `insert_final_newline = false`, `csharp_using_directive_placement = inside_namespace`); `CodeStyle.DotSettings` / `Inspections.DotSettings` are the rider layers it is paired with. Only `build/.editorconfig` is scoped to the Fallout project.
- Fallout-generated workflow files (`.github/workflows/CI.yml`, `Publish.yml`) carry an `<auto-generated>` banner: edit the `[GitHubActions]` attributes in `build/Build.cs` and regenerate instead of hand-editing:
  `dotnet fallout --generate-configuration GitHubActions_CI --host GitHubActions`.

## Output conventions (why tests are brittle)

- Section order is fixed by `IssBuilder.Write()`: `Directives`, `[Setup]`, `[Components]`, `[Tasks]`, `[Types]`, `[Languages]`, `[LangOptions]`, `[Messages]`, `[CustomMessages]`, `[Dirs]`, `[Files]`, `[Icons]`, `[Registry]`, `[Run]`, `[UninstallRun]`, `[UninstallDelete]`, `[InstallDelete]`, `[INI]`, custom `Sections`, `[Code]`. A new section must be registered there (field + property + `Write` call) or it silently never appears. (`TASKS.md` puts the new `[ISSigKeys]` section after `[LangOptions]`.)
- Sections are emitted as `\n[{Name}]`, key/value sections as `Key=Value`, parameter sections as `Key: value; ` per entry. Strings get quoted with `"` (inner quotes doubled); enums are lowercased with `_` and `,` stripped (`ValueExtensions`), so `FileFlags.Sign | FileFlags._32bit` → `sign 32bit` in one flags token.
- Every model property is written in **declaration order**, so reordering properties in a model changes output and breaks `ReferenceData` expectations.
- Section builder property names on `IssBuilder` must equal their `SectionName` (`BuilderTests.NamingConsistency`), which is why `INI` and `ISSigKeys` keep their ISS spelling.

## Adding a parameter / section

1. Add the property to the model class in `Model/<Section>/…Entry.cs` (`ModelBase` → `Aux` dict for arbitrary params; `CommonParameterSectionEntryBase` adds `Languages/MinVersion/OnlyBelowVersion/Check`; `KeyValueSection` is for `Setup`/`LangOptions`-style sections).
2. Add a builder method **with the exact same name** in `Builder/…Builder.cs`. `SetPropertyValue` resolves the property by `[CallerMemberName]`; a typo compiles fine and throws `NullReferenceException` at runtime. (`replace.txt` holds the regex used to generate these one-liners.)
3. Add it to the abstraction interface in `Builder/Abstractions/` and re-expose on `IssBuilder` if it is a new section.
4. Set it in `BuilderTests/TestBuilder.cs` and list it in the matching `…Tests.cs` `ReferenceData` dict. `ParameterSectionTestsBase` / `KeyValueSectionTestsBase` use reflection to require **every** model property as a key, so a missing entry fails the test rather than being silently untested. Deprecated (`[Obsolete]`) properties count too.
5. Flag enums: unique powers of two (`EnumTests` fails on duplicates), `: ulong` beyond 31 bits, `_32bit`/`_64bit` naming because C# identifiers cannot start with a digit.
6. ISS values that cannot be derived from the member name (e.g. `enhanced/nopassword`, `pbkdf2/220000`) get an `[IssValue("…")]` attribute instead of relying on the lowercase transform. Colors and scripted booleans use the `IssColor` / `IssYesNo` value types (implicitly convertible from `long`/`string`), never quoted strings.

For one-off ISS parameters that have no typed model property, use `Parameter(name, value)` (writes through `Aux`) or `Sections.CreateParameterSection(...)` / `CreateKeyValueSection(...)` — that is the intended escape hatch, not a reason to add types.

> `IssValueAttribute`, `IssColor` and `IssYesNo` are introduced by `TASKS.md` commits 1/4/5. Until those land, format such values as plain `string` and do not invent the types ad hoc.

## Conventions

- Block-scoped namespaces with `using` directives *inside* the namespace, 4 spaces for `.cs`.
- Nullable reference types are off by default; only `IssBuilderException.cs` opts in with `#nullable enable`.
- Public members carry no XML docs requirement (`CS1591` is suppressed), but anything mirroring an ISS directive/flag should link to `https://jrsoftware.org/inno-setup/documentation/?topic=<anchor>`.
- Deprecations are never deleted silently: mark with `[Obsolete("Removed in Inno Setup <version>: <replacement>")]` or `[Obsolete("Obsolete since Inno Setup <version>: <replacement>")]`, keep the member compilable, and keep it covered by `TestBuilder`/`ReferenceData`.
- Do not "fix" output line endings or clean up `Environment.NewLine` usage in `CodeTests`/builders — generated ISS line endings are platform-dependent by design (the builders use `WriteLine`, and `CodeTests` compares against `Environment.NewLine`, so it passes on Linux too). The suite is **fully green locally** (86/86); treat any red test as a real regression, not an environment quirk.

## CI / release

- `.github/workflows/CI.yml` and `Publish.yml` are **Fallout-generated** from the `[GitHubActions]` attributes in `build/Build.cs` (regenerate, don't hand-edit).
- Gitflow: CI on `develop` and `feature/**`; NuGet publish on `master` and `release/**`. Both run `dotnet fallout Test Publish` on `windows-latest` with `NUGET_API_KEY` / `ALL_PACKAGES` secrets and upload `artifacts/packages`.
- The package version is hard-coded in `src/InnoSetup.ScriptBuilder/InnoSetup.ScriptBuilder.csproj` (`<Version>`) — bump it there for releases.
- Default Fallout target is `BuildSetup` (publish `DemoApp` → build `.iss` → `ISCC.exe` → setup exe in `artifacts/`), Windows-only; `artifacts/` also holds previously produced demo installers.
